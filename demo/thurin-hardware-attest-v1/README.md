# Thurin Hardware Attestation v1

## SAMA5D3 + NeoPGP + Trusted Review + QR Transport

This experiment demonstrates a hardware-backed OpenPGP attestation compatible
with the current Thurin attestation verifier.

A Thurin Ethereum ownership statement is:

1. generated on the host;
2. transported to a SAMA5D3 signer by QR code;
3. reviewed on a trusted display;
4. physically approved;
5. signed by a NeoPGP secp256k1 hardware key;
6. returned to the host as a standard OpenPGP Signature packet by QR code;
7. assembled into an OpenPGP clear-signed artifact; and
8. independently verified by both GnuPG and `@thurinlabs/identity-kit`.

The private key never leaves the NeoPGP card.

This is a **SAMA5D3 + NeoPGP research-card experiment**. It is not a test of
the retail Keycard product or the Keycard Shell OpenPGP implementation.

# Host Statement Generation

The statement was generated with the current Thurin CLI:

```bash
./node_modules/.bin/thurin attest \
  --statement \
  --owner terricola.eth
```

The statement was saved locally and transported as a prototype KC1 QR request:

```text
KC1|OP=PGP_SIGN|MSG=I control the Ethereum address: 0x99fa48ccea8a38cde6b437450ff9bbddafaa4fc8
```

The QR layer accepts printable ASCII only.

No signing digest, fingerprint, public key, private key, or OpenPGP signature
was supplied by the host in the request.

# Trusted Signer

The dedicated experiment signer is:

```text
embedded/sama5d3/thurin_attest_v1.c
```

Build helper:

```text
demo/thurin-hardware-attest-v1/build-signer.sh
```

The existing QR signer was copied into a dedicated experiment so the previous
working SAMA5D3 demos remained unchanged.

This adapter is intentionally narrow.

It accepts only the statement shape:

```text
I control the Ethereum address: 0x<40 hexadecimal characters>
```

It is not intended to be a general-purpose OpenPGP cleartext-signing service.

# Board Clock

The SAMA5D3 does not retain a useful real-time clock across all development
sessions, so its clock is initialized from the host before the signing test.

Example setup:

```bash
source ~/.config/keycard-openpgp/demo.env

NOW_UTC="$(date -u '+%Y-%m-%d %H:%M:%S')"

ssh -i "$SSH_KEY" root@"$SAMA_IP" \
  "date -s '$NOW_UTC' && hwclock -w && date -u"
```

For this run the board reported:

```text
Fri Sep 25 01:27:11 UTC 2026
```

The signer fails closed if the board clock is clearly uninitialized.

# What This Test Proves

This experiment demonstrates that a Thurin ownership statement can be signed
without placing the OpenPGP private key on the host running Thurin.

The proven path is:

```text
Thurin CLI
    ↓
ownership statement
    ↓
request QR
    ↓
SAMA5D3 camera
    ↓
strict statement validation
    ↓
trusted display
    ↓
physical approval
    ↓
local OpenPGP digest construction
    ↓
NeoPGP secp256k1 hardware signature
    ↓
OpenPGP Signature packet
    ↓
response QR
    ↓
host optical recovery
    ↓
OpenPGP clear-signed artifact
    ↓
GnuPG
    ↓
Good signature
    ↓
Thurin identity-kit 1.4.0
    ↓
verified: true
```

---

# What This Test Does Not Prove

This experiment does not claim that:

- the retail Keycard currently supports this exact workflow;
- the Keycard Shell OpenPGP port is complete;
- the prototype KC1 QR envelope is a final production protocol;
- the SAMA5D3 experiment is a general OpenPGP cleartext signing service;
- an Ethereum registry transaction was submitted;
- the attestation was published to a Thurin registry.

The test intentionally stops at local cryptographic and application-level
verification.

---

# Relationship to Keycard Shell Work

This repository also contains ongoing work to implement OpenPGP functionality
on Keycard Shell.

That work is separate.

The SAMA5D3 + NeoPGP setup is the reference research platform used to prove
protocol and hardware-signing concepts before or alongside work on the more
portable Shell target.

The result here is useful because it demonstrates that the Thurin pre-signed
attestation model is compatible with a signer where the OpenPGP private key
exists only on external hardware.
